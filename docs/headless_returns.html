Headless returns

Implementation reference · 20 October 2026. Live carrier acceptance is required before release.

Enable the workflow

  1. Apply migrations/042_headless_returns.sql after migrations 035–041. The migration creates a private return-command receipt table; it does not change balances.
  2. Save a default active RETURN address in Settings. Its saved version is checked again before purchase. This is a merchant-maintained address, not proof of independent postal verification.
  3. Enable and validate the tenant’s native carrier connections. Existing TEST/SANDBOX and LIVE purchase controls remain mandatory. Ordinary Sendcloud credentials cannot purchase test labels.
  4. For customer payment, configure the existing Stripe checkout and webhook integration with matching carrier/payment environments. An owner or administrator creates the checkout link. Verified payment funds the merchant’s exact booking basket; unused credit remains in that workspace. No customer wallet or automatic refund is invented.
  5. Configure BOOKING_PAGE_URL to your public HTTPS application origin and a strong existing QUOTE_LINK_SECRET of at least 32 characters for shared drop-off links. QR links are signed for one document and expire after 24 hours. Provider document hosts must also be explicitly approved in PARTNER_DOCUMENT_ALLOWED_HOSTS. Otherwise documents remain available only through authenticated downloads.
  6. For signed store intake, enable Enable signed return requests in the store connection settings. The saved operator must retain an active dispatch role; customer-paid returns require OWNER or ADMIN.

Authenticated return command

POST /api/v1/shipping/prepare-return accepts a JSON array of 1–20 commands. Authenticate with the requesting workspace user’s valid access token. Never put a Supabase service-role key in a storefront or browser. Supply exactly one shipment_id or order_reference; references also match tracking and store-order IDs and must resolve uniquely.

[
  {
    "order_reference": "EINVIO-1024",
    "idempotency_key": "b60e266c-389a-42fb-bc3a-fb0a9ba932ce",
    "charge_bearer": "RETAILER_PAY",
    "maximum_price": "10.00",
    "paperless_requested": true
  }
]

Generate a fresh UUID for each intended return and retain it when retrying delivery. The maximum price uses the shipment’s quote currency. The API returns per-item outcomes and counts; HTTP 200 for a batch is not proof every item booked. Inspect every result.

OutcomeMeaning and next action
BOOKEDNative label confirmation and existing financial settlement succeeded. Response includes shipment ID, tracking, label download and paperless availability.
PAYMENT_REQUIREDShare the Stripe checkout URL with the payer. No return label has been purchased yet. The existing verified-payment worker completes eligible bookings.
PROCESSINGOriginal command is in progress or was interrupted. Query status; do not create another return command.
REVIEW_REQUIREDInspect the existing shipment, reservation and payment. No automatic mutation replay occurs. An operator must reconcile uncertain carrier or payment outcomes.

GET /api/v1/shipping/return-requests/{request_id} requires the same workspace authentication. It observes completed card bookings and can recover an appended EasyPost QR form using GET only. It never repeats a purchase. The original object-shaped endpoint remains compatible and prepares quotes without purchasing.

Storefront and marketplace gateways

Submit the same JSON array to POST /api/v1/integration/return-webhooks/{store_id}. This is a normalized merchant-controlled gateway contract, not an implementation of Shopify return-event payloads, Amazon RMA approval or automatic purchases on refunds. All matched shipments must belong to the configured tenant and store.

Send X-EasyInvio-Timestamp as Unix seconds and X-EasyInvio-Return-Signature as a hex HMAC-SHA256 using the saved store webhook secret. Sign the exact UTF-8 request bytes:

signed_bytes = timestamp.encode() + b"." + str(store_id).encode() + b"." + request_body
signature = hmac.new(webhook_secret.encode(), signed_bytes, hashlib.sha256).hexdigest()

Timestamps must be within five minutes. Redelivery uses the same command IDs. Existing storefront tracking synchronization preserves the return lifecycle and never marks the forward order fulfilled by a return. Shopify reverse-delivery updates still require a reviewed reverse-fulfillment reference; unsupported native marketplace updates remain held for review.

Carrier documents

  • Sendcloud: only return options advertising functionalities.labelless=true receive delivery_option=drop_off_labelless. A returned labelless document is exposed only when the carrier response confirms that delivery option and supplies a document. Other services use printable labels.
  • EasyPost: USPS Label Broker requires an enabled USPS Returns account. After label purchase, a durably fenced POST /shipments/{id}/forms requests form.type=label_qr_code. Failure retains the confirmed label and charge. A later status read can recover the form without another POST.
  • Shippo and other carriers: printable return handling remains available where the existing native return contract supports it. No undocumented universal QR flag or synthetic QR image is sent.

Only show “no printer required” when paperless_available=true. A shared link grants one drop-off document, not account access. It is a bearer capability: share it only with the intended recipient. Carrier restrictions determine eligible locations; a return is never advertised as accepted at every post office or depot. The stored source is shipments.logistics_metadata.return_dropoff_qr_code_url; clients receive a scoped application URL rather than private provider credentials.

Manual and conversational use

Use Create return in the manifest to select retailer billing or a customer card link and an optional price ceiling. The browser prevents double submission and clears the dialog when the identity or workspace changes. Alternatively send Return order EINVIO-1024 or Create a return for tracking DPD-7712 in authenticated web chat or signed WhatsApp. These explicit chat commands authorize a retailer-paid full-parcel return. Missing references are collected without inventing order IDs.

Twilio’s existing bounded webhook deadline still applies. A timeout does not prove failure: check the durable return and shipment status in the web app rather than submitting a second purchase. Commands interrupted before completion require operational reconciliation.

Scope and validation

Fresh return prices use current approved connections and exact Decimal customer totals. The lowest eligible price wins; budget carriers win equal-price ties. Partial provider results stop automatic selection because they cannot establish the cheapest available option. No carrier availability or universal QR coverage is guaranteed.

This entry point returns the entire originally measured single parcel. Partial contents, changed packaging and grouped multi-piece returns require explicit measurement/review. International goods require a fresh customs signer and HS review; outbound consent is not reused. One durable full-parcel return command is allowed per original shipment; another key cannot bypass it. Failed commands require support review rather than automatic replay. No migration was applied or live provider purchase performed during development.
