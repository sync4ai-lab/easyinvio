# Dual-role dashboard

`index.html` is a complete single-file HTML5 dashboard with Tailwind browser utilities, inline CSS fallbacks, native JavaScript state, SVG charts and no UI framework. Tailwind is loaded from `@tailwindcss/browser@4` on jsDelivr; the inline styles keep core layout and operations usable if the CDN is unavailable. Existing carrier quotes, Decimal billable-weight requests, CSV batching, manifest/label preview, wallet checkout, invoice auditing, HS predictions and declaration metadata remain connected to their original controllers.

The sidebar and mobile bottom navigation expose Overview, Speed Quote Matrix, Manifest, Box Profiles, Wallet and the Customs Harmonizer drawer. Box profiles are stored locally under the current tenant/user key and apply dimensions/actual weight to the existing quote calculator. Up to 50 validated profiles can be saved; this is browser storage, not a server-synchronized packing catalog.

Before sign-in, the two role buttons display explicitly labelled demo scenarios with the requested £759,000 revenue, £166,980 net-profit illustration, 42 SMEs, £4,320 client spend, £342.10 wallet and 184 labels. The demo exception histories include the requested WhatsApp/map-resolution text, but these are marked sample scenarios and do not assert that a message, map verification or carrier correction actually occurred.

After sign-in, `GET /api/v1/profile` verifies platform-owner authorization using `PLATFORM_ADMIN_USER_IDS`; otherwise it uses the existing signed JWT and active tenant-membership check. The frontend does not trust a user-editable profile role or decoded JWT to grant platform access. Platform owners automatically open the macro dashboard. Client accounts cannot use the toggle to access live macro analytics. Profile and metric state are cleared across role/session changes and stale authenticated responses are discarded.

Platform reporting uses owner-protected `/api/v1/admin/analytics/dashboard`, excludes sandbox tenants and displays currency-specific gross revenue, stored gross markup and active non-sandbox tenants. Net accounting profit is not available from the schema; the live UI identifies margin correctly rather than fabricating the requested demo 22% net yield. The carrier donut uses actual booked package volume; live historical trend charts are not synthesized when the API does not provide a time series.

Clients load their isolated `/api/v1/analytics/reports`, wallet, tickets and manifest. Label count means confirmed booked packages, not an instrumented count of printer activations. Warehouse cards derive average cost by destination from up to 200 manifest rows. Transit days are marked pending because those manifest responses do not include dispatch/delivery timestamps. Figures have a selectable UTC reporting range; wallet balance is current, while manifest lane costs describe the current retrieved manifest.

Support rows expand their recorded AI remedies. Manually Intervene opens a note form and persists to an authorized support-ticket route; demo interventions remain local. POD actions open only a stored HTTPS evidence link in a new tab, or explain that no proof has been supplied. No fake live POD token/image is generated.

Migration 012 adds `support_tickets.manual_note` and has been applied to the connected sandbox. The new profile, platform report, tenant/owner ticket listing and intervention routes are implemented in `backend/dashboard_portal.py`. Owner routes verify platform permissions separately; client routes scope reads and updates to the authenticated tenant. No public roles or Supabase credentials are embedded in the HTML. A platform owner who wants to use client operations must also have a valid tenant membership/claim.

Validation includes the retained frontend controller tests plus dual-role metrics visibility, demo badges, owner-toggle denial, box-profile application and backend authorization/Decimal report tests. Native browser rendering was not tested in this session because no browser surface was available.
