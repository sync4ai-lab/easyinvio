# Universal store integrations: local and UAT release

Implementation starts from 58d0ab2 on feat/universal-store-integrations. No Hallmark visual redesign is included.

## Activate deliberately

1. Review migrations/057_universal_store_integrations.sql and apply it once after 056 using your normal migration process. Development did not apply it to the shared database. It enables platform codes and creates rate limits, short-lived checkout cache, callback events and verified return sessions. Portals remain disabled until a merchant explicitly enables a policy. Do not deploy web/worker source using these tables before the migration is present.
2. Restart the local-development launcher with the existing private .env.local. No additional .env values were required or altered. The ordinary launcher uses WEB role with background jobs off. Use it to check pages, configuration, explicit API retrieval and request handlers. A separately supervised WORKER with BACKGROUND_JOB_MODE=ALL is needed for Amazon notifications, tracking callbacks and delivery notices. WhatsApp-only mode does not run those jobs. Keep the existing single-active-WhatsApp-consumer procedure.
3. Store Integrations now obtains its 24-code capability directory from /api/v1/integration/platforms. Register a store; its active tier must permit store connections. Save encrypted credentials, then explicitly use Test connection. This is read-only but calls the actual provider; offline tests never used those accounts. A successful read does not establish write scopes, app approval or notification delivery.
4. Shopify accepts a canonical hostname and an authorized token or supported own-organization client credentials. WooCommerce REST needs HTTPS origin plus consumer key/secret; its native signed webhook path still works. eBay needs an authorized seller bearer token; BigCommerce additionally needs store hash; Wix needs site ID; Magento needs the HTTPS store origin and authorized REST token. Token refresh/consent outside the existing Shopify/Amazon mechanisms remains platform-authorized/manual setup; it is not a one-click installer.
5. Custom Website and bridge platforms use an HTTPS retailer origin, generated key ID and signing secret. Copy the one-time secret into server-side secure configuration. Optionally configure a same-origin tracking callback; enable Live Tracking Write-Back only after the receiver verifies signatures and durably deduplicates event IDs. Rotation invalidates the previous signing secret, including any native webhook configured with that same secret. Coordinate both ends.
6. Public returns portal lets an owner/admin choose a unique slug and explicitly authorize the return window, payer and maximum postage. Copy its /returns/{store_slug} URL into the merchant website. The current automated shopper flow supports delivered, original single-parcel domestic returns under the GBP policy; international/changed packaging is merchant review. The merchant's current subscription and policy are rechecked before spending. Shopper contacts come from the original order, not arbitrary notification destinations. Carrier QR is conditional, never generated as pretend postage. No merchandise refund/restock is performed.
7. For UAT, deploy the tested feature through your deliberately chosen UAT process only when ready. Use matching web and worker sources from this commit. This work does not merge main/uat, move domains, deploy Vercel or modify Gupshup callbacks.

Run tests/test_universal_stores.py plus the existing store, ecommerce, dispatch, help, hosting, headless-return and security suites. HTTP providers are mocked. tests/test_universal_stores_postgres.py uses only explicitly configured disposable in-memory PGlite; never point the test fixture at DATABASE_URL. Stop the preview when finished. Production build: python scripts/build_vercel.py --bundle, then verify with the normal build command. Both are local packaging, not deployment.

## Native and bridge limits

The 24 directory codes do not imply 24 native OAuth integrations. The capability registry and /help/supported-platforms distinguish the seven existing/new native platforms, Custom Website, and API bridges. No native Etsy/TikTok/PrestaShop importer, SFTP collector, installed Make/Zapier app, Amazon tracking write-back or marketplace merchandise-refund program is claimed. Native order retrieval is explicit, bounded and review-oriented; split/partial allocation is rejected. eBay/BigCommerce/Wix/Magento REST adapters require acceptance testing with the merchant's actual authorized account before public launch.

Checkout rates use the ordinary tenant pricing engine and require carrier-valid exact addresses, measured weight and dimensions. They return customer prices without wholesale costs/credentials, reuse a tenant/store-bound cache for at most 90 seconds and enforce shared SQL request buckets. Binding a shipment/payment still requires the normal fresh quote and explicit booking. No AI or carrier request occurs just by opening a portal, looking up an order or loading the directory.

LIVE with write-back disabled stays PENDING/LIVE_DELIVERY_DISABLED. Only explicit TEST with write-back disabled may simulate. Setting provider_environment=TEST does not make a merchant platform account a sandbox: live write-back is an explicit real remote mutation. Historical SIMULATED_DELIVERED rows were not automatically replayed because the original environment cannot be proven from the outbox alone; review them before any deliberate remediation. Native uncertain sends retain reconciliation holds; bridge receivers must deduplicate stable event IDs on retry. Inspect ecommerce_tracking_outbox, store_callback_events and Amazon import activity.

The hosted portal uses ReturnReviewService's existing explicit service-selection, reverse_logistics_requests ledger and payment-gated document/notification machinery. This preserves the shared return lifecycle instead of introducing a second purchase implementation. Public shoppers cannot edit prices, addresses, payer, carrier selection or notification destinations. Existing authenticated reverse-return APIs remain available.

## Connection and documentation experience

The local landing page now has 24 filterable sales-channel cards and five carrier cards. Card details distinguish native adapters from signed API bridges; signup does not bypass subscription or provider requirements. No third-party logos load at runtime. Asset sources and raster exceptions are recorded in `docs/landing_brand_assets.md`.

In Workspace → Store Integrations → Connection settings, only the selected platform's fields appear. Custom Website and API bridges show copyable store/key IDs, the intake URL, a browser-generated 256-bit signing secret option, and the configured returns link. Saved secrets remain unrecoverable; replacement requires updating the sender. The returns shortcut opens the existing policy authorization form and never silently activates spending.

Visit `/help/connect-custom-website` or `/help/supported-platforms` for business-owner quickstart and developer tabs. Code examples use private environment variables and the existing HMAC contract; Copy Code never sends a request. Browser acceptance is available in `tests/integration_experience_browser.py`, using the offline preview on port 8017 and mocked API calls.
