Store intake
POST /api/v1/integrations/ecommerce/orders-sync?store_id=<registered UUID>
Shopify: use the same app signing secret as the authenticated connection and the canonical myshopify.com hostname. The receiver verifies the raw-body Shopify HMAC before normalization. Nullable native address fields and verified SKU weights are supported. New intake uses UNFULFILLED. Existing legacy intake remains compatible.
Amazon: configure the seller ID, marketplace IDs, SP-API region, LWA app Client ID/secret, authorized seller refresh token, verified SKU weights and a strong destination key through Store Integrations or ECOMMERCE_CONNECTORS. Order-address access requires Amazon approval. Create an ORDER_CHANGE SQS subscription. EventBridge Pipes can forward the original notification body to an API destination; use batch size 1 and an input transformer returning the original notification JSON, rather than the SQS wrapper or a batch array. Use API-key header x-easyinvio-amazon-key matching the saved webhook secret. Use a public HTTPS origin. The receiver acknowledges a durable notification with HTTP 202, and a worker retrieves authoritative Orders API v2026-01-01 details. Only wholly unshipped merchant-fulfilled orders are imported. Review missing SKU weights, addresses, permissions or unsupported currencies in Import activity, then retry after correcting them. Public app registration, seller authorization and AWS subscription creation are external prerequisites, not automatically performed by saving this form.

Booking and settlement
POST /api/v1/shipping/confirm-booking uses the private offer snapshot and existing reserve/purchase/capture workflow. Funds are reserved before contacting the provider. Successful confirmation atomically captures the wallet reservation, writes one CAPTURE ledger entry and records the confirmed booking. Replays do not repurchase or debit again. Definitive rejection releases reserved funds. Uncertain outcomes and Sendcloud 202 announcements retain the reservation for reconciliation. The JSON API reports label_status=LABEL_CREATED while the established financial status remains BOOKED; these are deliberately distinct state domains. Request Accept: application/pdf for the confirmed printable label stream. Pending Sendcloud announcements return HTTP 202, never an empty final label. Tracking links use the branded manifest; provider URLs remain private. Stripe funding remains validated against signed webhooks or retrieved paid, tenant-bound Stripe snapshots; redirects alone never credit funds.

Statement audit
Wallet & Billing includes CSV/XLSX upload and saved disputes. Required columns:
upstream_shipment_id,currency,invoice_weight_kg,wholesale_cost,residential_fee
Common equivalent column labels such as Carrier Reference and Billed Weight (kg) are recognized; unrelated columns are ignored. Weight units must be explicitly kg. Use kg and all-inclusive tax-exclusive carrier wholesale totals. One worksheet, maximum 1000 consolidated carrier-reference rows, maximum 5 MB; no formulas. If multiple native accounts share a reference, submit carrier_account_id to disambiguate. Matching uses tenant-bound native shipment/transaction references and confirmed bookings only. Different currencies and unknown/ambiguous references require review rather than invented FX or matches. Residential charges are flagged only when server-stored address verification confirms commercial use. Weight differences must exceed 0.1 kg. Residential and wholesale differences are not added twice. Confidence 100 means exact comparison to stored evidence, not certainty of carrier liability. Flagged findings and an email complaint draft are stored privately in billing_disputes. Email drafts are not automatically sent. Identical uploads reuse the saved dispute; changed invoice values require a revised reference.

Carrier tracking and alerts

Native signatures or the encrypted Shippo URL token remain mandatory. EXCEPTION records durable support work; a background wake-up stages tickets and opt-in merchant WhatsApp payloads. Twilio requires an approved sender, enabled support delivery, a public signed status callback and a valid template or customer service window. These gates remain enforced. Accepted sends are not reported as delivered. DELIVERED closes open review tickets, records a system resolution activity, cancels unsent alerts and saves approved carrier POD evidence. No delivery proof is fabricated.
