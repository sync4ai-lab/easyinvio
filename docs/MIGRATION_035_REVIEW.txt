Corrections to the proposed design
1. JSONB supports indexing; an unindexed array does not inherently prevent item
   validation. A broad GIN package index does not accelerate numerical summation
   for a single shipment. Goods lines get a normalized private table with indexed
   tenant/HS/origin and SKU fields, generated exact totals and tenant-bound FKs.
   PostgreSQL reference: https://www.postgresql.org/docs/16/datatype-json.html
2. Every box includes its own actual packed weight as well as three dimensions.
   Array indices are sequential, 1-based and capped at 100. Numeric validation
   rejects missing/nonpositive measurements and invalid precision. Flat legacy
   fields mirror box 1; they are not the aggregate shipment mass. The existing
   parcel_count=1 CHECK is extended only for a fully captured multi-piece parcel.
3. Total goods net mass must be <= total packed mass, allowing for packaging.
   Allocated goods must fit their individual box. Deferred validation allows
   atomic edits, while parent locks serialize concurrent goods writes. Submitted
   goods and package measurements are immutable. Unknown historical arrays remain
   empty; no repeated-box inference or guessed goods/currency backfill occurs.
4. Store sales fulfillment, return lifecycle and return-case progress are separate.
   Historical fulfillment defaults to UNKNOWN rather than incorrectly labelling
   all existing orders UNFULFILLED. Return parents have tenant-bound foreign keys.
   New return/exchange outbox jobs are held for reconciliation so the CURRENT
   forward-only worker cannot accidentally fulfill the original order.
5. A boolean alone is not a credential security boundary. PostgreSQL now locks
   connection identity on insert and seals existing rows. Standalone credentials,
   endpoint, environment and account identity cannot be overwritten or unlocked.
   Operational priority/activation edits continue to work. Shared tenant mirrors
   may only synchronize from their existing trusted platform catalog record.
   last_security_audit_at remains NULL until a real audit occurs.

Current application compatibility
The new package/goods snapshots are empty until the backend implementation.
Existing single-box booking uses its existing validated fields. Current admin

Shared provider changes continue through the existing catalog synchronization.

Backend implementation following confirmed migration execution
-------------------------------------------------------------
RatingRequest accepts multi_parcel_dimensions with sequential box_index,
length_cm, width_cm, height_cm and actual_weight_kg. Decimal math computes
max(actual, L*W*H/5000) independently per box, rounding upward to 0.001 kg,
then sums. Carrier APIs receive each physical box, not duplicated aggregate
weights. ClientRate exposes package_count and package_weight_summary.

Order preparation persists normalized shipment_goods_items. Each multi-box
goods line needs package_index; SKU and box assignment remain immutable
through checkout. Marketplace preparation supports the measured-box JSON
array; single-box fields must match box 1. Net goods weight must not exceed
packed weight, globally or for an allocated box.

EasyPost uses native Orders for multiple packages (maximum 100). Shippo uses
its multi-parcel Shipment and retrieves every Transaction after one buy;
current implementation limits UPS to 40 boxes and FedEx to 12. Sendcloud v3
requests multicollo and quotes only options explicitly supporting it. v2 and
unverified regional multi-box adapters are excluded. Existing TEST/LIVE and
purchase-capability guards continue to apply. Group purchases require all
package labels; uncertain/partial results remain reserved for reconciliation.
Every package PDF and unique tracking number is retained. Group invoice mass
checks compare the sum of packed weights rather than box 1. Delivery becomes final
only when all packages are delivered. Group cancellation/refund and grouped
return purchase are guarded pending complete native reconciliation support.

Return jobs remain separate from forward fulfillment. Shopify synchronization
requires an existing approved ReverseFulfillmentOrder belonging to the original
order, matching quantities and read_returns/write_returns permissions. It uses
reverseDeliveryCreateWithShipping, not fulfillmentCreate, and performs no
refund, return approval, disposal or restocking. A send fence is committed
before mutation; recovery verifies native state rather than resubmitting.
Amazon return synchronization remains RECONCILIATION_REQUIRED until a specific native
seller return program is configured; no generic Amazon return endpoint is
invented. Local physical return scans update IN_TRANSIT/RECEIVED independently.

GET /api/v1/integration/tracking-events exposes lifecycle and review codes.
POST /api/v1/integration/tracking-events/{event_id}/return-reference links a
verified Shopify reverse fulfillment order, prior to submission.
POST /api/v1/integration/tracking-events/{event_id}/reconcile verifies native
tracking without creating another label or forward fulfillment.

POST /api/v1/admin/carriers/{account_id}/replace-credentials requires a real
platform administrator with a verified authentication-method timestamp within
five minutes. JWT issue time or refresh alone does not qualify. Submit a new
request_id, new_api_key and reason. The old sealed identity is retained and
disabled; a uniquely named, sealed replacement is created disabled, with a
new tenant/account-bound encrypted envelope and private audit entries. Verify
and activate the replacement before quoting. Shared catalog credential changes
also require fresh authentication; mirrored tenant credentials remain sealed.
